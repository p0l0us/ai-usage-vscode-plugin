# W11 frozen reset confirmation interface
- Config `codex.autoReset.confirmationRequired` boolean false; automation `resetConfirmationRequired?: boolean`. W12 maps.
- Engine automatic and non-forced redemption use existing single policy. Forced Rotate now remains account rotation only (existing no-redemption behavior).
- Pending decision engine generated: UUID id, accountId/name, availableCredits, windows (labels/percent/reset), reason, expiresAt (five minutes). Internal digest binds credential fingerprint, active id, full settings (counted window labels), quota/credit data; fetchedAt excluded. No native reset invocation or persistent reset attempt write for preview.
- `reset.confirmations` read lists pending (also no UI); `reset.claim` takes id and connected clientId, returns decision or null. Only one client owns dialog. `reset.resolve` takes id/approve boolean, only owner approves, anyone cancels. Claimed disconnect cancels; expiry/stale/shutdown prevents spend. New reconnect may inspect unclaimed state; cancelled/expired same facts suppressed until facts change (prevents dialog storms).
- `resetConfirmation` event contains decision; clients claim before showing, list once at adopt. Capability `reset-confirmation` gates client integration.
- Approval under account lock checks current settings/native identity/credential/quota/credits digest, consumes decision once, reruns existing rotate policy with ephemeral approval bound to the originating async execution scope. A globally reserved queued approval cannot authorize another sweep. Immediately before native redemption recheck admission/dispose/request cancellation/claim ownership/native identity/config+digest. No approval replay or trust in UI eligibility.
- W13 new test/resetConfirmationParity.test.js: existing real socket background/embedded hosts, synthetic reset injection; approve/cancel/noUI/stale account/credit/multiwindow/disconnect/shutdown/expiry. New deterministic automation tests cover opt-out + one-use + digest checks.
